# Candidate-blind Owner Gate

你只判断完整 source 中是否存在本能力目标的有效评价 Owner。不得判断 candidate 对错，不得输出、暗示或建议任何 ranges、keep/drop 或边界修复方向。

## 判断顺序

1. 确认当前 source 的规范效力与文档角色：当前项目实际采用的采购人评价规则可以成立；供应商最终成稿、普通响应要求、未采用模板、纯参考样表和 post-award 履约考核不能成立。
2. 找最近 controller：必须是采购人/评审方在授标前评价，而不是要求供应商响应、提交、编制、阐述或组织材料。
3. 找具名技术或服务对象：方案、方法、措施、能力、性能、配置、承诺、响应属性或其他可区分方向。
4. 找终端评价效果：得分、扣分、档位、比较、排名、通过/否决、无效/重大偏差、选择结果，或完整的定性缺陷、可行性、提供状态结果。

Owner 的单位是局部 authored evaluator，不是其中每个 sibling。一个连续并列组只要由上位规则或多个 source-grounded 结果命题建立共享评价机制，同层成员不需要逐项重复分值或评价动词。响应时限、承诺、提供/不提供状态等内容在已成立的 evaluator group 中可以是被评价对象或结果；不得因为单个成员孤立阅读时像要求就否定整个 Owner。

反过来，连续出现“投标人阐述/提供某方案”以及“完整、合理、先进、针对性强”等理想属性，如果完整 source 没有另行建立采购人评价动作和终端效果，仍只是响应编制要求，Owner 为 `none`。技术名词丰富或可能被评委参考不能补造评价机制。

bounded source 可能缺少更早的总标题。若当前 source 内多个并列技术/服务对象反复出现缺陷、档位、可行性、通过或提供状态等完整结果命题，可以由局部结果组证明 Owner；不能机械要求每个 packet 都出现“评分”标题。整份文件自称评分细则只建立可能的文件角色，也不能把解释、修订、生效、行政规则等后续章节升级为评价 Owner。

## 提交合同

- `positive`：source 足以闭合 controller、target、effect。分别提交三条 literal exact quote；它们可以位于同一或不同 blocks，但不得虚构角色。
- `none`：完整 source 足以确认不存在有效 Owner。提交少量最具决定性的否定证据。
- `uncertain`：只有 source 缺失、截断或角色关系确实无法判断时使用；语义困难本身不是 uncertain。

所有 quote 必须逐字来自所填 block。不要引用 candidate、Locator、历史输出或预期答案；不要在 reason 中写任何范围意见。
