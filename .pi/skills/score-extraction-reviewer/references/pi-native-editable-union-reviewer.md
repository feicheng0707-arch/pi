# Candidate-Aware Complete-Delta Reviewer

Use the frozen accepted single-prompt contract only for file-role classification, the `owner_section` eligibility gate, and the definition of a valid technical evaluation direction. Its mutation scope, container-first range policy, harmless-width tolerance, isolated-pointer deletion rule, and range output contract are Locator behavior and do not govern this review. This role requires exact minimum block membership under the closure rules below.

The trailing candidate is a high-quality but fallible Locator that already solves the normal case. Use it as the scope anchor, never as correctness evidence. Do not rebuild a wider answer merely because a chapter, owner heading, or table container is relevant. Change membership only when the source proves a residual omission or pollution.

Read the complete immutable source, then derive the complete symmetric delta from the candidate with four bounded passes:

1. Identify the purchaser-authored, pre-award evaluation `owner_section` or package locus represented by the candidate. If the candidate is empty, locate any valid owner from the full source.
2. Audit candidate edges and every atomic member. Remove procurement requirements, technical specifications, qualification/conformity screens, price/procedure siblings, response-file templates, contract/post-award duties, and titles whose immediate artifact is non-target. A broad evaluation-procedure controller cannot merge an earlier conformity, formality, or qualification stage into a later business/technical subcontroller; the later subcontroller starts a new minimum bridge unless source makes the stages indivisible. In a sibling list, a generic parent heading belongs to its first immediate child or to the inseparable group, not to a later technical sibling; a self-identifying atomic technical reference does not need those generic headings.
3. Recover omissions only inside that same active owner/locus or through a literal authored dependency from it. Treat any mechanically repeated candidate-linked reference neighborhood only as an attention aid, then audit every atomic block in that owner span for omitted technical/service score-allocation gateways and repeated direct technical cross-references, including target-category references separated by business or price siblings. A separately authored technical component/weight reference and a separately authored technical scoring-standard reference are distinct gateways when each occurrence itself assigns a current weight/effect or directly points to the retained detailed evaluation artifact. Independent authorship alone is insufficient: a relay that only points to another summary, preface, or already-retained pointer is not a direct gateway. Also check for a source-written bridge, uninterrupted peer group, attached evaluation-evidence note, split atomic continuation, or governing preamble. Retain each qualifying direct reference as its own atomic block; do not inherit adjacent business, price, or heading siblings.
4. Recheck the final boundary to the end of the source. Do not add a distant requirements chapter, another lifecycle copy, a supplier response form, a historical/template method, or an unrelated package merely because it contains similar technical vocabulary.

For a combined business/technical bridge to one retained mixed evaluation artifact, keep the shortest complete parent-through-technical-child group. For multiple current alternative evaluation methods written as one uninterrupted preamble immediately before the retained detailed rule, keep that contiguous preamble. Neither rule crosses an intervening owner, table, chapter, or later price artifact.

Submit every canonical source block ID whose membership must toggle relative to the candidate. The empty array means the candidate is already exact. Submit no verdict, reconstructed membership, narrative, ranges, quotes, or ledger.
