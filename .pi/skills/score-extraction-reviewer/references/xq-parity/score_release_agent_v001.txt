必须按 controller-first 顺序处理每个候选 scope：

1. 先确定最近显式 controller 与边界：当前项目/标包、投标或履约生命周期、文档角色、评价 Owner、被评价对象、同级章节/表格切换。style、outline、numbering、block kind 和相邻地址只是结构证据，不是语义 Owner；全为 Normal 时仍必须从 source 判断角色切换。“响应方案”“投标文件内容”“技术文件目录”“编制要求”默认由供应商写作/提交角色支配，后代方案名、内容清单和质量形容词不能反向补出评价 Owner。这里必须继续检查 source-grounded 关系桥，而不是把默认角色当作绝对排除：同一项目和当前评价阶段中，若上游已证明的评价因素集合与后续响应子项存在显式对应，或至少两个有区分度的因素在名称、数量和顺序上形成完整一一映射，则映射子项及其紧邻的提交/格式要求是被评价材料，应随因素保留；比较子项集合，不把响应容器标题当作额外因素。单个通用主题重合、部分映射、未来另定标准、跨生命周期重复或无关子项不能建立关系，封面、身份签署和其他未映射范围仍可删除。
2. 再判断该 scope 是否存在 gateway target。source 必须证明当前投标/评标/定标阶段的评价主体或上位规则，对至少一个具名技术/服务响应方向的内容、质量、组成、能力、承诺或比较属性执行评价，并存在分值、档位、扣分、比较、优劣、通过判断，或针对该具名方向的内容构成/质量审查机制。机制不要求固定分值：若语句以评价结果或档位陈述某个具名方案/承诺完整或不完整、合理或不合理、可行/可操作或存在缺陷、提供或未提供等状态，而不是仅命令供应商编制材料，也属于定性机制。供应商“提供/编制/阐述/承诺”的动作以及“完整、合理、针对性强、优化、先进、亮点”等预期质量词，若没有 source 中显式评价主体及其结果/档位/得分关系，只是响应内容要求，不是机制。不得用“内容改变可能影响评委印象”的常识补出 evaluator。明确评价父规则，或多个相邻同层成员在同一 scope 反复出现真正的 evaluator result/grade 结构，才可以证明评价组。
3. 评价组一旦证明，必须先判 group membership，再做 standalone 判断：沿候选两侧枚举连续同层兄弟，只用肯定的项目/标包、生命周期、文档角色、Owner、被评价对象或同级 controller 切换终止。组内成员继承评价主体和机制；简短的响应时限、可度量承诺、独立方案方向、响应属性、提供/不提供状态、编号跳号或未重复分值/评价词都不是删除理由。selected 标记和邻接本身不能证明组，但组已经由 source 证明后，也不得再要求每个成员单独重复 gateway 三要素。做对象反事实时，应判断改变该成员表达的响应实质是否会改变组内评价，而不是只看本块是否重复评价动词。
   上游候选构造 review/patch 是非权威信号，必须重新核对；但若它已把某块认定为遗漏组成员或明确写入 group rationale，你要删除该块时必须在 source 中指出肯定的项目/标包、生命周期、文档角色、Owner、对象或同级 controller 边界。仅说本块没有重复评价词、分值或档位，不足以推翻组成员关系。
4. 若一个 scope 没有 gateway target，则资格/形式、通用响应性或强制符合性、无具名方向的无偏离门槛、最低价与报价修正、价格排序与候选推荐、澄清磋商、报告签署、评价行政流程、普通采购要求、响应目录、空参考指针和签约后绩效考核都不能借宽泛标题取得目标身份；该 scope 应删除或清空。
5. 若一个明确评分 controller 下已经证明至少一个 gateway target，发布单位立即切换为该 controller 支配的完整局部评分容器，不再逐个对子项重复 standalone target test。该容器中直接说明评分规则的同层商务/形式/报价因素、重复局部标题、分组、表头、分值、阈值、上限、得分或不加分条件、无效/废标后果以及局部适用或合同衔接说明，都随有效因素保留。尤其不能因为“下文已有完整表格”或“标题语义重复”删除紧邻并直接引出该表格/因素组的项目名、评分表名、局部章节名或分组头；原文提取必须保持 source 的局部层级和阅读入口，重复不等于可分离污染。反过来，支配大量混合投标程序、合同或行政内容的宽泛上位章节，不是局部评分入口，不能仅因远处后代出现评分规则而新增或保留；标题必须与评分因素形成直接、局部的引出或分组关系。只有封面身份信息、与该容器无关的独立标题，或肯定的新 controller 才可作为标题删除边界。
6. 肯定的同级新 controller、文档角色切换或评价生命周期终止，都能切断已证明的评分容器。尤其要逐块判断评价结果是否仍在形成：计算分数、比较方案、处理并列、确定排序或选择中标对象仍属于评价阶段；一旦 source 预设中标/成交/入围对象已经确定，随后只负责通知结果、合同磋商、签约、公告、送达或履约的块，就是强生命周期边界，即使编号连续、没有新标题、style 全为 Normal，也不得继承评价组身份。新的资产/设备/人员/项目构成清单、工程量或数量表、技术规格矩阵、采购需求表、合同履约考核、独立最低价章节等事实型 scope，若没有评分列、评价动作或与已证明因素的局部适用关系，即使没有 Heading style、紧邻评分内容或沿用编号，也属于可分离非评分范围。反过来，含评分因素、分值、档位、扣分、证明要求、阈值或无效后果的表格仍属于评分容器，不能因同时出现数量、价格或技术事实而切断。
