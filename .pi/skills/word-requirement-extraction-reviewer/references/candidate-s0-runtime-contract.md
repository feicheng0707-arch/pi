# Candidate-S0 Runtime Contract

本文件只约束 Candidate-S0 Challenger/Finalizer 实验路线，并进入 capability hash。它不替代 active 三调用 Pi-native 路线，也不改变旧路线 identity。

## 固定执行序列

Harness 将成熟 Single-Prompt Candidate 的 exact block set 冻结为 `S0`。成功路径最多两次 provider call，失败路径可以提前终止：

1. 独立 Challenger 读取完整不可变 source、`S0`、由 Harness 对全部 `S0` blocks 做的扁平、无筛选、无语义机械 source projection、只列每个 run 地址/首尾/singleton 状态的机械 run queue，以及同一 source 内的有界 exact-delimited-string occurrence index、机械地址授权和严格 tool schema，通过唯一结构化 tool 提交一次有界 challenge：最多八个非权威 typed hard-carrier root review、八个 exact remove partitions、两个 neutral remove-audit partitions 与两个 exact add partitions；
2. `S0` 非空或存在有效 add envelope 时，独立 Finalizer 再次读取完整不可变 source、`S0`、同一份机械 run queue、同一份未经 Challenger 选择或改写的 exact-delimited-string occurrence index、有效 typed root review 与 challenge navigation groups，并通过唯一 strict tool 同时提交全 `S0` sparse precision delta、Challenger-envelope add delta与最多三十二个全局 hard-carrier root veto。`S0` 为空且不存在有效 add envelope 时在一次调用后正常结束；只有 rejected root challenge 也不改变该机械 no-change。Finalizer 不重复接收 `S0` 原文 projection；它只用完整 source、canonical `S0` ranges、机械 run queue、机械 occurrence index 和无自然语言结论的 typed review 地址工作。

无 retry、第三次调用、投票、best-of-N、逐 block ledger、答案驱动路由或失败后换模型重跑。两个角色的 model/profile、Prompt、schema、容量与调用上限必须在第一次语义调用前冻结；不得按 case、source、Candidate、模型答案、历史结果或 evaluator 切换。

`MECHANICAL_EXACT_DELIMITED_STRING_OCCURRENCE_INDEX_JSON` 只从本次完整 source 中提取 `《》`、`“”`、`「」`、`『』` 和英文双引号内 2-120 字符的 seed；seed 可在同一个 canonical block 内跨 CR/LF，随后统一折叠 Unicode 空白并保持其他字符、大小写和标点精确不变，再按 packet source order 定位包含同一 literal seed 的 blocks。Harness 最多扫描 source-order 最先出现的 256 个 distinct seeds；每个 block 对同一 seed 最多记一个地址，只保留在 `S0` 内外均有 occurrence 的 seed；每侧最多八个 block IDs、每项最多十六个、全局最多六十四项，按 seed 首次出现顺序确定性截断。它是 bounded、non-exhaustive 的 block locator，不判断引用方向、同一 module、固定/填充状态、对象/功能匹配、intro applicability、Owner、recovery、membership 或材料性；命中、未命中和任一层上限截断都不改变 challenge、add envelope、root veto、ordinary delta 或发布权限。两个角色必须回到完整 source 独立建立全部语义证据。

## Challenge 与发布权限

- `hard_carrier_root_challenges` 最多八项，只提交 `carrier_type + inclusive root + exclusive exit/EOF + projected_s0_anchor_block_id + source_conclusion + supporting IDs`。它只是 Challenger 的 bounded attention/navigation，不是删除授权、保留票、双钥匙或 veto；Harness 逐项机械校验地址，保留自然语言 conclusion 到 trace，只向 Finalizer转发 typed 地址与 supporting IDs。Finalizer 可拒绝、收窄、独立发现未挑战 root，且 challenge/veto 是否同址只进入 trace。
- exact remove partition 只能定位 `S0` 内且位于四类 hard carrier 之外的地址；exact add partition 只能定位 `S0` 外地址。所有 source-proven hard-root descendants 均由 Finalizer 的 typed veto 独占处理；Challenger 提交对应 root challenge 后必须对 descendants 保持沉默，不得把它们放入任何 exact/audit/add partition。每个 partition 必须有非空 source-grounded claim 和最多 24 个最小充分、真实 source supporting IDs，但 Harness 不读取 claim 含义；不得用逐目标 supporting-ID ledger 消耗输出预算。
- Challenger 必须对每个 Candidate run 完成逐 canonical block 的内部 `ATOM|HEADING|excluded` 闭包；singleton、首端和尾端只决定扫描优先级，不是抽样许可。语义路由顺序固定为：先肯定建立 recovery 的累计四链；成立时进入 `recovery_boundary_scope` 并据此约束相关 root challenge 的 exit；不成立且仍受 hard root 支配时提交一个最少最大 typed root span 后对 descendants silent；root 外同一最小 peer scope 同时含 survivor 与多个可分离 hole 时进入 `mixed_atomic_scope`；只有同质、肯定、无 survivor 的目标才进入 exact remove。材料性只在 source-certain outputs 超过各自协议上限时参与排序。
- neutral remove-audit partition 只给 Finalizer 提供一个有界 `S0` scope 的优先导航，不是额外删除授权、整段删除结论、不确定项收容器或 keep/remove 投票。`mixed_atomic_scope` 与 `recovery_boundary_scope` 各最多一项、各不超过 96 blocks，两条通道合计去重上限 192 blocks；前者只处理最小普通 mixed atomic/heading scope，后者必须覆盖由 earlier incorporation 建立的一个完整、连续 `later module intro→真实 peer exit` recovery boundary，不能互相占用。Harness 从 submitted ranges 自行机械展开、计数并校验预算；audit 与 exact remove、其他 audit 必须机械零重叠。
- Finalizer 的普通 `Delta-` 可落在完整 `S0`，包括 Challenger 未挑战地址；普通 `Delta+` 仍只能落在 `ADD_ENVELOPE`。每个 ordinary remove 都必须由 Finalizer从完整 source 独立肯定证明无 `ATOM|HEADING` provenance，且不得与有效 root projection `V` 重叠。Harness 只按集合机械拆分 challenged 与 independent ordinary remove 供 trace，不把该分类变成不同语义门。
- Finalizer 可独立提交四类 hard carrier 的 typed `carrier_type + inclusive root + exclusive exit/EOF + projected_s0_anchor_block_id`；root 可以位于 `S0` 外，但 anchor 必须属于 `S0` 且落在该 source-order span 内。Harness 只据此机械证明投影非空并形成 `V=S0 intersect [root,exit)`，不读取标题、正文、carrier 或 anchor 的语义真伪。hard-carrier veto 不是 ordinary exclusion 的替代，只能表达四类 categorical root。
- Finalizer 对每个拟提交 hard root 都必须逐一反证它将跨越的 later Candidate islands：不能因 Challenger 没有提交 recovery audit、把 recovery scope 错标成其他 review kind、或 source outline 仍位于 carrier 之下而省略独立 recovery disconfirmation。只有完整 source 肯定证明该 island 仍连续属于 carrier，root 才能跨过；否则必须在最早 boundary-independent peer 前结束或撤回。
- 最终集合唯一由 Harness 计算 `S=(S0-Delta--V)+Delta+`。单个 Finalizer root/exit/anchor 地址无效或投影为空时只拒绝该 effectless veto 并记录 trace；若仍有其他有效 delta/veto 可发布则继续，全部 veto 均无效且无其他有效 effect 时 fail-closed。任一 add 地址落入有效 veto span、有效 veto spans 彼此重叠时仍属全局自相矛盾并 fail-closed。有效 veto 可机械 shadow challenge 地址；Finalizer 不得把 root descendants 重复写入 ordinary delta。普通 `Delta-` 必须严格落在 `S0` 且与 `V` 零重叠；ordinary 通道单独删除完整非空 `S0` 被机械拒绝。
- 全局 tool/top-level schema/source-address 失败必须 fail-closed。单个 root challenge 或 ordinary partition 的 range、方向、membership、重复、预算或 supporting-address 失败逐项记录 rejection trace；有效项仍可进入 Finalizer并标记 `partial` coverage。无效 root challenge 本身不阻断非空 `S0` 的独立 Finalizer；它不能产生修改。唯一例外是任一 submitted `recovery_boundary_scope` 被拒绝时整次 fail-closed，因为丢失该 typed boundary lock 后继续发布会改变其协议含义。若提交过 non-root partition 且这些 non-root partitions 全部无效、同时没有有效 root challenge，则不调用 Finalizer，Candidate 原样保留并 degraded；若因其他有效 group/root 进入 Finalizer，被拒绝的 non-root 地址仍属于完整 `S0` independent precision audit，不获得 keep 票。
- 非空 `S0` 无论 challenge 是否为空都进入一次独立全 `S0` Finalizer；空 `S0` 且不存在有效 add envelope 时才是一次调用的正常 no-change。任何 Challenger 或 Finalizer provider、turn、全局 schema/tool、越权 delta 或 veto 自相矛盾都保留 Candidate并 degraded。

## 容量、输出与 trace

- Challenger 与 Finalizer 都只允许一次强制 `submit_final_selection` strict tool call；默认禁止 thinking，且普通 auxiliary text 不参与语义。Challenger output cap 固定为 12,000 tokens，与 provider model max 和 schema 合法上界对齐；Finalizer auxiliary text 只记录字符数和 SHA-256，`forwarded=false`；Challenger 任何 auxiliary text 都是 contract failure。
- 两个完整 source context 都必须在第一次 provider call 前做最坏输入容量预检。Challenger preflight 必须计入 occurrence index 与 provider-visible strict tool schema；Finalizer preflight 覆盖完整 source、canonical `S0` ranges、同一份机械 run queue、同一份 occurrence index、固定 Prompt/schema、Challenger 最大输出、最多三十二个 veto、Finalizer 最大输出和 safety reserve。model-facing `remove_review_ranges` 始终等于完整 `S0`，`add_review_ranges` 等于有效 add envelope；`hard_root_review_groups` 只转发 typed root/exit/anchor/supporting IDs。exact partition 在 canonical 合并前按原始 submitted range 拆成独立 group，保留稳定 partition/range index，每组只附 target range 外按 packet source order 前后各两个机械邻接 ID；不转发 shared claim、shared supporting IDs 或完整 target block ledger。audit group 仍转发 typed kind、target ranges、机械 block count和 supporting IDs。Challenger 的 `source_conclusion` / `audit_basis` 完整保存在 raw/normalized trace但不进入 Finalizer context。
- trace 必须记录 packet/capability/input SHA、冻结 model/profile、Prompt SHA、实际调用数、usage、延迟、coverage、raw/normalized Challenger response、Challenger claims `forwarded=false`、rejected partitions、Finalizer raw tool arguments、canonical root challenge/veto、root challenge-veto trace-only match、challenged/independent ordinary remove、root remove、occurrence index scanned seed count、seed-scan truncation、eligible/emitted entry count、entry truncation、两侧 block-ID truncation entry count与 serialized character count、最终机械 decision和失败类型。每个 emitted entry 也必须分别标明 Candidate-side 与 outside-side 地址是否被截断。实际 index 已进入两个 role input SHA；算法版本、delimiter 集、跨行行为、seed 长度、归一化、匹配、去重、顺序与全部上限进入 capability identity。canonical root 地址原样保留 exclusive block ID 或字符串 `"EOF"` 及 submitted S0 anchor，不得另造第二种 EOF sentinel。capability hash 不得包含 case、packet、Candidate ranges 或 evaluator 信息。

## Harness 边界

代码只负责 Pi Agent harness 和原子机械能力：packet/schema/SHA、完整 source 序列化、供 Challenger 使用的全部 `S0` blocks 扁平无筛选 source projection、只含地址/首尾/singleton 的完整 run queue、仅由 paired delimiter seed 与 exact normalized literal occurrence 形成的 bounded block index、地址范围展开与压缩、按 submitted range 拆组、packet source-order 机械邻居、source-order root span、集合 membership、challenge/veto 地址授权、challenged/independent 集合分账、容量/调用/超时预算、final delta 应用和 trace。

代码不得读取标题或正文含义，不得按关键词、行业、项目、case ID、source hash、历史结果、Candidate 表现或 evaluator 选择 keep/drop、Owner、carrier type、root/exit、audit scope、challenge、范围或修复方向；不得按 Candidate 地址位置筛选所谓高风险子集。exact literal occurrence 只能提供地址，不得被代码升级为引用、纳入、附件、recovery 或适用性结论。把完整 `S0` 统一作为 ordinary remove 的机械 authorization 是固定、无语义的协议，add 仍只能来自 Challenger envelope。代码可机械列出完整 Candidate runs、地址与 block count 供模型导航和预算核对，但不得解释 `source_conclusion` / `audit_basis`，也不得从这些元数据形成语义裁决。
