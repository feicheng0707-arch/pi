# Word 单包采购需求范围语义合同

完整不可变 source 是唯一事实来源。Candidate 是成熟但可能出错的第一判断，不是 source 证据。

## 正向目标

保留能够改变技术方案大纲、独立章节或正文事实基础的当前项目原文：

- 采购对象、服务对象、工程范围、专业系统、货物/服务类别、工作包和交付边界；
- 功能、性能、规格、接口、兼容、材料、工艺、安装、调试和试验要求；
- 服务内容、流程、响应机制、组织人员、岗位职责、驻场和连续性要求；
- 实施、进度、资源、质量、安全、环保、风险、应急、交付、验收、培训、运维、质保和售后；
- 合格采购需求来源内展开的技术参数表、对象/设备/材料表、服务清单、工作包、项目专用技术义务和详细附件载体。

只选标题、概述或“详见附件”指针而漏掉同一 Word 内已展开的详细正文/表格，属于 source-fidelity failure。标题、表头、直接说明、跨页续段和末项应与其目标载体保持必要闭合。

一旦判断某个项目范围、质量、安全、质保、验收、技术标准或其他合格章节应保留，必须继续检查该标题之后、下一个同级 Owner 边界之前的实质正文，并让标题与正文共同闭合。图片占位、空行、分页或短续段不构成章节结束；不能保留章节标题或概述，却删除同章承载具体义务、参数、措施、响应时限或责任的正文。表头、清单明细、跨页续行和末项同理。

载体闭合不得反向跨越起点。独立技术附件、清单或图纸从其自身标题、名称或首个明确内容 block 开始；其前方仍在上一载体内的签署主体、日期、签章、落款、页眉页脚和版式图片不得因紧邻附件而获得 membership。进入合格载体之后的图片占位、分页和短续段仍不构成结束边界。

## 载体硬排除与合格来源

以下四类载体不属于 `requirement`：招标/采购/资格预审公告及其摘要；投标人/供应商/响应人须知及其前附表、正文和通用程序；投标/响应/报价文件格式、投标函、授权书、声明函、承诺函、目录模板、封面和签章占位模板；合同条款及格式、合同协议书格式、通用或专用合同条款模板、履约考核模板和合同附件范本。

边界完整的投标方/供应商承诺、响应承诺、无偏离承诺或声明章节，若其实际功能是在成交前要求投标/响应主体就未来履约作声明、确认、保证或承诺，就是投标/响应格式 Owner。它不要求出现空格、签章位或“格式/模板”字样；内部即使逐项复述质保、质量、服务、人员、交付等真实履约义务，也从该 root 到 peer exit 整体排除，不能再启动主要直接效力或义务存活反事实。孤立的“承诺/保证”措辞不能建立该载体；位于四类载体之外、由采购人直接命令中标后执行的义务仍按履约事实保留。

四类载体之外，对孤立的成交前提交/承诺/确认/声明包装执行 `response_wrapper_survival_attack`。先剥离“在响应文件中填写、提交、自行承诺、确认或声明”等包装；若同一不可分 block 的剩余内容仍直接要求成交供应商实施、配置、保障安全或质量、交付、验收、服务或达到具体结果，整个 block 保留。只有 source 已建立边界完整的响应/承诺载体，或包装是可安全分离且不承载任何履约 duty 的纯证明/表态 atom，才可排除。单个 block 出现“响应文件”或“承诺”不能独立触发 subsection-level `pre_award_stage_gate`；该 gate 仍要求明确 root、peer exit、多个共同定义准入的证明子项及成交前后果。

这些载体即使出现当前项目名称、技术词、通用责任、唯一技术性文字或未填写的未来义务，也不得作为采购需求来源。技术事实同时存在于合格来源时，只从合格来源保留；若只存在于排除载体，本 capability 不负责迁移。合格来源包括采购需求、用户需求书、技术标准和要求、项目专用技术条款、技术规范、设计/图纸说明、设备材料技术要求、技术清单、有效技术附件和采购范围。

交叉引用不转移载体 Owner。合格需求章节中的“详见附件/合同附件/考核表/响应表”等指针，只证明存在引用关系，不证明被引用内容属于 requirement。必须在被引用内容实际所在的结构位置重新判 Owner；公告、须知、投标/响应格式、评分、资格、合同条款及格式或其附件范本中的内容，即使详细、唯一、与需求正文一致或被需求章节明确引用，也仍按其载体排除。标题—正文—表格闭合只能在同一合格 Owner 内延伸，不能跨越硬排除边界。只有边界独立的技术规范、需求书、图纸、清单或有效技术附件可以因引用进入范围。

四类硬排除载体之外的独立“商务要求”“履约要求”“交付条件”“售后要求”等章节必须按实际义务而非标题判断。直接规定当前项目工期/服务期、地点、采购范围、质量、保修/质保、交付、验收、服务响应或其他可执行履约事实的 block 属于 requirement；价格、付款、结算、保证金、投标有效期，或没有直接工作义务的纯违约救济、解除、争议解决、合同成立/生效、适用法律和一般法律风险分配等可安全分离 block 不属于 requirement。一个章节同时包含多类内容时只能按可寻址边界分别裁决，不能用“商务”或“法律”标题删除整个混合章节。

“主要直接效力”只适用于 source 已经证明位于四类硬排除载体之外的可寻址 block。公告、须知、投标/响应格式或合同条款及格式尚未结束时，外层 Owner 是终态门槛；不得再用局部实施、服务、质量、安全、验收、人员或项目专属事实覆盖该排除 Owner。退出这些载体之后，以计价、报价构成、支付、结算、扣款、审计、发票、保证金或价格调整为主要效力的 block，即使引用工程量、完工、验收或质量保证金作为金额依据、付款前提或结算触发条件，仍是纯商务；“验收合格后结算”不等于采购人另行提出验收技术要求。只规定违约赔偿/救济、合同解除、生效/成立、争议解决、适用法律或一般法律风险分配，且没有直接工作义务的 block，是纯法律非工作内容。以实施、提供、配置、施工、交付、维护、响应或达到工期/质量/安全结果为主要效力的 block，则是履约事实，即使附带费用已含、不另支付、违约后果或其他法律后果也不改变其主要效力。只有同一原子 block 内两类效力确实不可分割时，才为技术事实保护 source fidelity。

载体之外的每个拟删除 block 都必须通过一次义务存活反事实：暂时去掉审批、报审、备案、费用、扣款、违约、解除、赔偿等附带后果后，若剩余主句仍直接要求实施、配置资源、编制/提交计划方案报告、形成或保存记录、交付、限时替换/补齐、响应、按平台执行或达到结果，则它仍是 requirement。费用措辞不得吞掉资源提供义务：主句若要求供应商负责当前实施所需材料、耗材、工具、设备、设施或人员的提供、准备、保障或可用性，同一不可分 block 中费用由其承担、已含或不另支付只是附带商务处理；只有资源仅作为丢失、损坏、浪费、赔偿或计价对象，或条款只分配费用而不要求实际提供资源时，才可按纯费用/救济删除。直接工作效力不局限于供应商祈使句：对当前项目成果的准确性、完整性、误差或质量负责，采购人对成果进行检查、复核、验收并据此要求纠正，以及规定适用技术标准的现行版本、替代关系或优先顺序，都直接约束交付结果或履约基线；纯权利保留只有在与工作成果、质量阈值、纠正义务和适用标准均无关时才可删除。明确要求中标/成交供应商对当前项目的设计、施工、安全、质量或成果承担前置责任，同样分配履约治理责任；附带经济损失承担不取消它。语法上的否定前件或处罚结构不能替代直接效力判断。若不可分原子 block 在救济之前给出独立保证、禁止、质量/结果基线，或以一个具体的供应商可控制失败作为处罚前件，剥离后果后必须对该前件做极性归一，恢复其对应的正向动作或结果义务；及时维护、正确稳定的产品或版本、不侵权保证、避免返工等具体且可执行/可验收的 duty 均应存活。只有泛称违约、违规、与合同不符、造成损失或质量问题，且没有具体动作、阈值、交付结果或纠正责任时，才是纯救济触发器。相反，质量差错、违规、虚假成果或其他履约问题只作为扣款、赔偿、取消资格、解除、递补或依法追责的触发条件时，不产生独立质量 requirement；剥离这些救济后若没有独立供应商责任、成果责任、质量阈值、复核验收、纠正或工作动作，仍按纯法律/程序 atom 删除。保密条款若直接控制当前项目数据/资料的存储、处理、传递、复制、披露、留存、返还或销毁，就是数据控制履约义务；不能因同段另含保密协议、法律责任或成本承担而删除。要求按指定平台执行的主句也不会因末尾附带解除合同后果而消失。合同签订后或履约期间，采购人书面提出标准、范围或条件变更且供应商必须配合、执行、调整或补充的，是直接 change-control duty；同一不可分 block 中价款、费用或补偿另行协商只是附带商务处理，不能把整段删除。中标后的提交、审核、批准、备案和记录管理是履约流程，不是成交前采购程序。只有成交前证明/响应动作，或剥离附带后果后不再存在直接工作义务的可分离 block，才可删除。成交前未提出异议/偏离即视为完全响应、同意、接受或无偏离，或要求在响应文件中提出异议/偏离的规则，是响应解释/证明 atom，不是中标后工作义务；即使位于四类载体之外也应作为可分离 outside-carrier exclusion。成交前证明 atom 从实际要求填写、附上或提交证明的 operative block 开始；相邻中性标题、序号、空标签或上一个履约 block 不因连续地址自动继承该 Owner，除非 source 证明它们共同建立资格/响应载体。后续合同扣款或法律章节不能反向改变前一平级技术章节的 Owner。

Candidate 已包含一个处罚/扣款/救济 cluster 时，必须做一次 `consequence_cluster_attack`，避免“簇内有一个真实 duty，因此全部保留”的注意力投票。经极性归一后仍有具体动作、结果、数据控制或质量基线的 block 保留；可分离的泛化违约触发、处罚依据指针、只服务处罚的事件定义、确认/扣除/付款执行，以及在相邻详细义务已经保留后仅重复遵守要求并附处罚、却不新增动作/阈值/结果/纠正责任的 wrapper，仍是纯后果 atom。只对 Candidate IN 的纯后果 atom形成 remove；Candidate OUT 的同类内容不是变化。该攻击是一次粗粒度地址分区，不要求 ledger。

四类载体门与 `pre_award_stage_gate` 均已关闭后，对把成交后交接动作与商务、证明或救济语言混写在同一不可分 block 的内容执行 `performance_transition_attack`。成交后协调、盘点、与实际转移相连的验收、接收、接管、迁移、移交或返还资产、设备、材料、数据、账户、场地或在制工作，是实施启动或连续性义务。暂时剥离估值、折旧、价款、补偿、结算、承诺/证明和救济后，只要仍存在实际交接动作，整个原子 block 就必须保留；只有剩余内容纯粹分配金额、估值、所有权或付款且不要求任何实际交接时，才可删除。可分离标题仍独立判 membership。该攻击不要求 ledger。

四类载体之外的 subsection 中，标题和 child block 必须独立判 membership。一个 child duty 存活，不会为只命名价格、付款、结算、扣款、处罚、违约、救济、解除或争议等非工作后果的可分离标题授予 membership。若删除标题不会使存活 child 丧失必要语义，标题单独进入 outside-carrier exclusion；合格技术/服务/安全/验收标题或理解正文不可替代的标题仍与正文闭合。该原子标题规则不能替代载体门；已成立的四类 root 仍整体排除。

载体外的合同效力/文件关系 wrapper 仍是纯法律 atom：仅说明规范、附件或成果将成为合同组成部分、具有同等法律效力或以合同为准，而不新增技术标准、工作动作、交付结果或纠正责任时，应删除。只规定未尽事宜由双方协商/另行解决、却没有具体任务、流程、输出或时限的 catch-all，同样属于合同空缺/争议 fallback，不是实施协调 requirement。

载体 Owner 的优先级高于局部标题和内容。“项目专用技术条款”只指位于技术需求、技术规范或工程技术范围 Owner 下的项目专属技术条款，不包括合同载体中的“专用合同条款”“合同技术条款”“项目专用合同条件”或合同附件。只要一个范围实际属于合同协议、合同条款及格式、通用/专用合同条件或合同附件范本，它即使已经填写当前项目事实、列出具体服务职责、施工义务、质量验收或人员要求，也仍是合同 Owner，不能转解释为合格技术来源。公告中的“采购范围”、须知中的“技术要求”和响应格式中的“技术响应”同理，局部字段名不能覆盖外层载体 Owner。

四类载体采用结构包含硬边界：在公告、须知正文、投标/响应格式或合同条款及格式尚未结束时，其内部子标题、表格、附件项和项目专用字段仍继承外层排除 Owner。不能因为子标题写着采购范围、服务要求、技术要求、验收或已经填入当前项目事实，就在载体内部重新建立合格来源。只有边界清晰地退出该载体后的独立技术章节/附件，才可按自身 Owner 重新判断。

若可选 Word 结构图给出了 `outlinePath`，必须先解析保护岛起点的最近上级节点及其 source 文本，再寻找保护岛之前第一个同级或更高层级 peer boundary。较深层级标题仍是上级载体的结构子节点；章节名、附件编号、技术内容密度、居中、粗体、分页或表格不能单独把子节点提升为平级独立来源。只有 source 文本与结构关系共同证明已经出现同级或更高层级功能出口，才可重开 Owner。结构图不提供 Owner 标签，外层载体语义仍由模型判断；但在已判定外层属于四类硬排除后，不得无视仍指向该外层的 ancestry，仅凭局部内容技术具体建立 preserve island。

硬排除载体的起点不要求被 Word outline 标成顶层。若 source 在更宽章节内部以编号、加粗、居中或普通文字明确开始合同主要条款/合同格式、投标或响应/报价格式、投标人或供应商须知、公告或通知序列，该局部标题本身即可建立新的硬排除 Owner；其后服务期限、地点、质量、验收、技术参数、人员、内嵌附件、技术清单或其他项目专属子条款持续继承，直到 source 证明进入下一个同级功能区域。附件标题、编号重新开始或技术细节增多本身不构成 peer exit。不得因为外层章名同时包含“技术、服务、合同”或局部义务对履约有用，就跳过这个局部载体边界并启动主要直接效力切分。详细技术表也不能脱离仍开放的响应或报价格式 Owner。

每个争议边界都必须先完成一次紧凑、双向的 `carrier_root_exit_attack`。对拟排除区间，模型必须向前确认该区间从 source 实际建立的四类载体 root 开始，并向后寻找第一个 source-proven peer exit 或 EOF；对拟保留岛，必须逐内部子标题检查是否新开始公告/通知、须知、响应/报价格式或合同条款载体。没有实际 root 时不得创建载体；发现更早的平级 Owner 时，硬排除必须在其前停止；保留岛内部出现局部 root 时必须从该 root 切开并排除到其 exit。若有结构证据，争议 root/exit 必须与 `sc/path` 对账：更深层附件、技术标题、普通段落或表格仍是 active carrier 子节点，只有读取第一个同级或更高层级候选的 source 功能后才能重开。物理采购文件、邀请容器、Candidate 连续区间、后续合同章节或相邻另一类硬排除载体都不能替代 root/exit 证明。相邻的合同、响应格式、公告和须知即使地址连续，也必须按各自 Owner 分开表达，不能拼成一个覆盖中间独立技术来源的外层载体。

`sc/vc` 给出的 exit 只是当前物理 scope 的结束候选，不是语义 Owner exit。必须读取该 peer 的 source 功能：若仍是同一公告、须知、格式或合同 Owner 的下一部分、附件、表单或 sibling scope，就继续继承并沿同 Owner peer 链向后寻找；只有首个不同 Owner 的 peer root 才结束载体。任何已经成立的四类 root 都采用 root-closed exclusion：root 自身、全部后代、内嵌附件和连续同 Owner peer 都进入硬排除，直到语义 Owner exit；该区间内禁止再执行主要直接效力或义务存活反事实，也不得把 root 标题或任何技术子项写回 final。

父章若同时聚合技术、服务、合同、商务或其他内容，只是 mixed container，不形成整章统一 Owner。进入载体外原子判断前，必须完成一次 `mixed_container_root_sweep`：逐 child heading candidate 从 source 判断是否开始局部公告/通知、须知、投标/响应/报价格式或合同条款载体。若同一局部 root 下的付款、保证金、违约等子项被删除，而后续服务期、地点、质量、验收、人员或技术子项被保留，则形成非法 holey selection；除非 source 能否定该 root，否则必须排除完整 root→semantic-exit 区间。该 sweep 只要求一次粗粒度边界结论，不要求逐 block ledger。

公告载体不要求存在明示“公告”总标题。一个自包含区域若按对外通知功能连续给出项目概况、参与资格、文件获取、投标/响应递交、发布媒介和联系方式，则其中的项目概况仍是公告性摘要 Owner；它不会因为包含当前项目唯一或最具体的范围、规模、工期、质量事实而成为 requirement。只有 source 明确结束该通知序列并进入边界独立的技术来源后，Owner 才可重开。完整邀请文件中的其他并列载体仍须按实际功能分别判断，不能把本规则扩张为整份文件公告化。

在局部 Owner 分区之前先检验整文角色假设。若一个实际公告/通知 root 开始后，标题/称谓、开篇邀请报价或响应、内部连续编号、报价资料要求、递交与联系方式、落款及随附报价格式共同构成首尾连续、功能同质的单一对外沟通，并且直到真实结尾都不存在平级异质 root，整段沟通载体才属于公告/通知摘要 Owner。接受整文公告假设前必须做 `whole_container_disconfirmation`：只要 source 建立了平级、边界独立的资格、评审、合同、响应格式、需求书、技术规范、图纸、清单或有效技术附件 root，物理文件就是多载体采购容器。封面词、单个邀请动作、所有章节共同服务一次采购，或结尾仍有递交/联系方式，都不能把这些平级 Owner 合并为一个公告；外层采购文件/邀请容器不是第五类硬排除载体。

通知序列必须是一个结构连续、功能同质的区域，不能只因项目概况、资格、获取、递交和联系方式分别出现在同一物理文件的不同章节，就跨越同级响应格式、合同、评审、技术章节或详细技术附件，把全文合并成公告 Owner。出现这些异质同级载体时，外层文件是多载体采购容器；每个章节、附件和表格边界都必须重新判断 Owner。独立技术附件不因位于邀请文件末尾或属于同一物理文件而继承公告 Owner，仍按其自身功能和事实载荷判断。

一旦完整邀请文件已由同级异质章节证明为多载体采购容器，不得再创造覆盖全部章节的“邀请书正文 Owner”；`邀请书` 是文件容器名称，不是四类硬排除之外的第五种载体。邀请前言、通知摘要、获取/递交和联系方式等区域按实际公告/程序 Owner 排除；同级项目范围、采购内容、执行期质量安全、质保售后、技术标准和详细技术附件直接按自身 Owner 判断。它们不需要等待显式“邀请结束”句，顶层功能切换、同级章节过渡或附件边界本身就是可用的 source-proven boundary。只有实际承担通知功能的连续区域，才继承公告 Owner。

“同级”必须相对于具体公告/邀请载体自身的结构层级成立。顶层公告或邀请章节内部的项目概况、采购内容、采购范围、期限、地点、质量标准等次级标题、编号子节和表格，不会因为内容技术具体或局部编号完整就成为平级技术来源；它们持续继承外层排除 Owner，直到 source 进入与该公告/邀请章节平级的独立采购需求、技术规范、图纸、清单或有效技术附件。后续存在这些平级异质章节只能证明整份 Word 是多载体容器，不能反向提升前一公告/邀请章节内部的摘要子节。

封面总标题只描述物理文件，不自动定义整份文件的单一载体 Owner。“邀请书”“谈判/磋商/询价文件”或其他完整采购文件不自动等同于“招标/采购公告及其摘要”；只有实际承担公告、通知或程序摘要功能的区域才进入第一类硬排除。完整采购文件可能由多个同级语义载体组成；建立公告等硬排除边界时，必须依据整文目的、同级结构、前后过渡和区域实际功能，而不是由封面名称或首段邀请行为向全文继承。与邀请前言、资格、格式、合同和程序并列，且边界清晰地直接规定当前项目对象、范围、质量、安全、质保、验收或其他技术义务的区域，可按独立合格来源判断。真实公告正文内部的项目概况、采购范围和技术摘要仍继承公告 Owner；同级编号本身既不能证明退出，也不能证明仍在载体内。

当同一物理文件并列包含资格、报价/响应格式、评审、合同以及技术章节或技术附件等完整采购结构时，外层文件是多载体采购容器，不能把一个公告/邀请前言 Owner 继承到全部同级区域。第一类硬排除只覆盖实际承担公告、邀请前言、获取/递交/联系方式等通知摘要功能的区域；其他同级区域分别按实际 Owner 判断。真实的独立招标/采购公告仍整体排除，公告内部的顶层编号或技术摘要不因此成为合格来源。

必须区分完整邀请文件与公告文种。承载完整采购结构的竞争性谈判邀请书、询价邀请书、投标邀请书或类似邀请文件，不因含“邀请”二字自动成为竞争性谈判公告、询价公告、招标公告或公告摘要；前者按多载体采购容器处理。其邀请前言、获取/递交程序等区域排除，但边界独立的项目概况/采购内容、执行期质量安全、质保售后、技术标准和技术附件仍按实际 Owner 判断。资格章节内部的人员证书、安全资格和投标承诺属于资格/响应 Owner；退出资格章节后独立规定中标后履约、施工、质量、安全、质保或售后的区域，不能继续继承资格 Owner。

人员表或人员证书不是自动排除信号。若主要直接效力是证明投标人/拟派人员在投标前具备资格，或要求供应商填写、提交人员名单、简历、证书和承诺，则按资格/响应 Owner 排除。一个边界完整的投标/响应强制性要求章节或强制响应表，即使以未来时态列出拟投入岗位、人数、进场时间或证书，也仍是成交前响应载体。人员类 Stage Owner 必须先在 subsection 层级闭合：若一个有明确 root 与 peer exit 的人员 subsection 由多项证书、社保、资格承诺、无在建承诺或无效响应后果共同定义成交前准入/响应证明，则 root 标题和全部子项直到 peer exit 整体继承该 Owner；其中某一子项同时描述未来岗位、人数、进场或配置，不能单独重开履约 membership。只有 source 证明该 subsection 主要是成交后实际履约配置，填写、附证或承诺要求只是可安全分离的局部注释时，才把该注释作为 proof atom 单独排除。紧邻真实履约人员配置的可分离注释若主要要求响应文件填写、附上或提交姓名、证书、截图、社保证明或承诺，同样是成交前证明 atom，必须单独排除，不能因相邻岗位职责而获得 requirement membership。若 source 已退出公告、须知、资格审查、投标/响应格式和合同载体，边界独立的采购人要求直接规定中标后实际履约必须投入的岗位、职责、最低人数、执业条件、驻场/进场时间或持续配置义务，则属于 requirement；不得只因相邻文字含审批、违约或资格字段而删除。履约期的独立性、职业纪律、利益冲突申报和回避义务直接约束成交供应商及其人员如何执行当前项目，是实施与质量治理事实；只有主要效力是成交前证明投标主体或人员是否具备资格时，才属于资格/响应 Owner。必须依据实际 Owner、发生阶段和对履约组织的直接约束裁决。

章节标题不是唯一依据。必须按段落或连续区域的实际 Owner 和功能判断；若一个原子段落不可分割地混合排除载体与合格技术来源，优先保护合格来源的 source fidelity，不得用代码或关键词拆义。

## 成交前资格/响应 Stage Gate

四类载体之外进入逐 block 主要直接效力或 `duty_survival_attack` 之前，先执行 `pre_award_stage_gate`。若一个有明确 root 与 peer exit 的人员或强制响应 subsection，通过多个子项共同要求证书、社保、资格材料、承诺或其他证明，并以无效响应、不得参与或类似成交前后果定义准入，则整个 subsection 的主要 Owner 是成交前资格/响应证明；root 标题和全部子项直到 peer exit 整体进入 outside-carrier exclusion，内部某个未来岗位、人数、进场或配置子项不能重开履约 membership。只有 source 肯定证明 subsection 主要约束成交后实际履约，而证明要求只是可安全分离的局部注释时，才进入原子门并只排除该 proof atom。

## 错误方向硬排除

- 明确其他项目、其他包、冲突采购对象或冲突采购类型；
- 供应商已非空填写身份字段并形成第一人称投标响应、实施方案、配置或承诺成稿；
- 企业内部制度、岗位手册、培训教程、产品说明书等非采购文件；
- 不存在的段落号、非法范围或错误输出字段。

wrong direction 必须发生在合格技术来源中。四类排除载体里的复用项目名、示例地点、陈旧期限和其他字面冲突，不因字面不一致自动变成当前技术方向错误；它们按载体 Owner 排除。只有合格来源中的冲突信息以当前项目可执行的技术对象、范围或实施义务出现，才满足技术方向排除。

## 从零 membership 排除

独立资格、纯商务报价、纯评分办法、开评标程序、不承载工作内容的纯价格/付款文本，以及可安全分离且不规定直接工作义务的纯法律后果/合同程序文本，不属于理想 requirement 成员。四类载体硬排除适用于 residual review：若 Candidate 中存在可安全分离的公告、须知、投标/响应格式或合同条款及格式，应按 actual Owner 精确移除，不要求先证明冲突项目或错误技术工作。对四类载体之外的普通同包噪声，“从零时不选”仍不等于必须从成熟 Candidate 删除。

纯评分标题、评审办法、评分表结构、分值、得分条件、无效投标规则和低于成本评审由 score-position 或其他能力负责，不进入 requirement 输出。评分块只泛泛点名施工组织设计、服务方案、人员、业绩或其他技术主题时，其主 Owner 仍是评分，不得据此加入 requirement；优先保留评分块外独立存在的甲方编制要求。

纯评分表即使比技术编制章节列出更多评价维度，也不能获得 requirement credit。评分标题、评分表、评分行、评分项和得分条件内部的方案名称、子项清单、实施维度、优缺点、完整性、合理性、分值、扣分条件和“未提供不得分”均属于评分 Owner；无论 Candidate 是否已覆盖同一 deliverable、source 是否存在等价非评分载体，都不得以 source-fidelity omission 为由新增。

Owner 判断优先于局部技术词。普通采购要求段落若先独立、命令式地规定具体 deliverable，末尾仅附带评价后果，可按采购要求 Owner 判断；但地址合同以整段为原子单位时，不能为了取得评分表或评分行中的技术主题而新增整个评分主 Owner 段落。技术章节对评分表的交叉引用也不改变评分 Owner。

评分主 Owner 已存在于成熟 Candidate 时，应按实际边界精确移除；不能为了删除评分内容而伤害相邻合格采购需求。孤立且无法安全拆分的混合原子段落仍优先保护 source fidelity。

资格审查资料、商务响应、报价文件、开评标流程、磋商/谈判程序及“哪些内容可在程序中变动”等规则，不因属于完整响应文件组成而成为采购需求。

## 整文身份

任何局部段落 membership 判断之前，必须先确定整份 source 的作者关系、使用目的，以及它是单一 Owner 文档还是混合沟通/交接载体。判断依据是开头、中部和结尾共同呈现的任务关系、填写状态和整体结构，不是某个标题、称谓或技术词。

采购事实源不要求正式发布、盖章、招标编号或完整采购文件结构。采购人侧需求简报、技术交底、会议纪要、邮件/聊天整理、现场勘查记录、方案委托和内部 handoff，只要已经给出当前项目的具体对象、范围、现场事实、工作内容、技术义务，或明确要求供应商据此形成技术方案，均可作为 requirement source。typed `buyer_issued` 在本合同中包含这些采购人侧事实源，不表示其已经完成法律意义上的正式发布；公告、须知、格式和合同模板即使由采购人发布，仍按载体硬边界排除。

法律文书形态豁免不等于合同载体豁免。完整 source 若由合同双方/当事人关系、订立或履行合同的总领关系、连续条款、价款或结算、违约、生效、解除/续约、争议解决、签署盖章等结构共同形成一份自洽双边合同，则完整 source 的关系是 `contract`，不因标题出现“服务要求”“技术要求”“协议要求”、内部义务技术具体、采购人提供文件或项目已实例化而变成 `buyer_issued` 需求 handoff。只有合同真实结束后边界独立的技术规范、需求书、图纸、清单或有效技术附件可以重开 Owner。若 source 从头到尾只有该合同且无独立合格来源，正确结果为裸 `null`；主要直接效力测试不得在合同内部启动。

合同载体必须由 source 的实际结构和功能建立，不能从单个“合同、违约、保密、知识产权、审批、责任、扣款”词语推断。边界独立采购技术要求中的源码/成果交付、知识产权保证、保密与数据处理、网络安全、持续维护、周报记录、报审和替换义务仍按直接工作效力判断；只有进入明确的合同协议、合同条款及格式、履约考核模板或合同附件范本 peer 根后，内部后代才继承合同 Owner。后续合同章节不得反向吞并前一平级合格章节。

真实项目事实不足以单独证明采购需求 Owner；完整 source 的作者关系和使用目的仍须审查。但已经完成分析、设计和结论的报告、规划、研究或方案，也可能是采购人提供的当前项目技术依据，不能因为它在“交答案”、缺少招标措辞或没有显式委托句就自动变成 `non_procurement`。整文判空必须有肯定证据证明它是供应商交付物、企业内部材料、无关成稿、未实例化模板，或与当前采购任务不存在可用关系；完成口吻和文档标题只能触发对抗性检查，不能独立承担删除结论。若作者关系无法证明为错误 Owner，而 source 确实承载当前项目具体技术事实，Candidate 保留推定优先。相反，已填写供应商身份、第一人称自有能力/承诺、报价、人员设备、签章或明确提交关系等证据仍可证明完成的供应商响应。

若 source 整体是供应商已经完成并作为交付物提交的投标/响应/实施方案成稿，例如多处身份、人员、设备、报价、签章、日期、第一人称承诺或供应商自拟措施已经实际填写，则正确结果为裸 `null`。这类成稿通常会复制、引用或承诺遵守原采购要求；局部内容仍然技术具体，并不能改变其供应商响应身份，也不得从报价表注释、响应表、承诺或方案中切出一段作为采购需求。

整文供应商响应结论必须由 source 中实际存在的身份、提交关系、自有能力、自拟措施、人员设备、报价签章或第一人称承诺证明，不能由技术内容丰富或完成口吻推断。一旦完整 source 已由这些肯定证据证明为单一供应商交付成稿，不能再以“其中可能复制了采购要求”的假设阻止整文判空；只有 source 自身存在边界明确、上下文闭合、可独立归属采购人侧的原始要求块时，才保留该实际可分离块。对潜在复制来源的猜测不是 Candidate Defense 证据。

已完成供应商响应属于材料性错误作者方向，即使它描述同一个项目、同一种采购对象和表面相关的技术工作。下游若把供应商的自有平台、人员设备、自拟措施和承诺当成采购人要求，会直接改变事实 Owner；因此不需要另行证明存在冲突项目或冲突采购类型。Reviewer 的 `issue_type` 只是 challenge 分类，不改变 source Owner 与 exact add/remove 的独立裁决。

若 source 是采购人需求、供应商疑问/报价/建议和任务指令组成的混合沟通或 handoff，应按可分离 block 的实际 Owner 判断：采购人侧已实例化事实和方案委托可保留，供应商报价、已拟方案、内部判断和商务条件排除。存在供应商文字不等于整份 source 已成为供应商交付成稿；只有整体目的确为交付供应商方案、且不存在可分离采购人事实源时，整文 veto 才成立。外层确为供应商成稿时，只有边界清晰、上下文闭合、可独立归属采购人侧的原始要求才可分开判断；零散复制条款或规范性复述仍不构成独立事实源。

采购人发布的真实项目招标文件可以同时包含四类排除载体和合格技术来源。四类载体不会触发整文 veto，但其采购人身份也不会赋予 requirement membership；应排除公告、须知、格式和合同模板，同时继续检查独立的采购需求、技术规范、项目专用技术条款、图纸说明、参数表、工作包和有效技术附件。

“具有采购文件版式”不等于“已经实例化的采购项目”；反之，“缺少正式采购版式”也不等于没有采购事实。若完整 source 的开头、中部和结尾均只提供占位字段、示例、编制说明、空表和通用条款，且不存在任何已填写的当前项目对象、范围、工作内容、技术义务或与真实项目材料建立的可执行关系，则整份 source 是未实例化模板，按非采购事实源返回裸 `null`。模板中说明采购人未来应填写哪些内容，或枚举可能出现的采购类别，不产生 requirement credit。只要 source 任一位置存在真实当前项目的具体采购事实或方案委托关系，就不得套用该整文判空规则，而应继续按实际 Owner 完成全篇召回审查。

`instantiation=present` 必须由能够区分本次真实项目的已填写事实证明，例如实际项目名称、采购对象、地点/现场、明确范围、数量规模、具体工作包或方案委托关系。范本版本号、范本编号、通用法律依据、平台操作规则、默认期限、资格年份、通用质量标准、制式合同义务、空白技术响应菜单和“如有”方案模块都可在未实例化模板中预填，不能单独证明当前项目存在。若项目名称、对象、地点、规模、范围、期限和技术要求等核心锚点全部只是“见公告”“见技术规范书”等外部指针，而所指当前项目材料不在本 Word 中，则本 Word 自身仍没有可供技术写作使用的项目事实；通用条款具有法律约束力也不会把它转化为已实例化 requirement source。

整文实例化门槛与局部 requirement membership 正交。通用规范或质量基线不能单独把空白模板证明为真实项目；但完整 source 一旦已由其他具体事实证明 `instantiation=present`，四类排除载体之外的独立合格技术来源中，任何对当前项目可执行的质量、安全、环保、材料、施工、服务、验收或其他技术义务都属于事实正文。它不需要同时包含项目专属数值、设备型号或详细工作包，也不因文字可在多个项目复用、引用现行标准或篇幅只有一条而变成无事实壳。非事实壳必须确实只剩标题、占位、示例或未随当前 Word 提供材料的外部指针。

引用外部规范不等于只做外部指针。若独立合格技术来源直接要求当前项目的材料、设备、施工、服务、质量、安全、环保或验收必须遵守/达到所引用的法律、图纸、规范或现行标准，这种规范性纳入本身就是可执行义务，即使被引用文本未复制进 Word，也具有事实载荷。只有文本仅说“详见/以另附文件为准”、当前段没有声明任何义务且所指材料未随 Word 提供时，才是裸外部指针。

直接规范义务不得因“过短、通用、没有参数”而被降格。一旦项目由其他 source 事实实例化，四类硬排除载体之外的独立技术标准/规范章节只要使用“必须遵守/达到/符合”等关系把当前项目工作绑定到法律、规范或现行标准，就已经有当前事实载荷；数段正文、通用措辞、缺少型号数量或未复制标准全文都不改变这一点。

技术章节标题、空标题或仅指向未随当前 Word 提供的技术任务书/规范书/附件的交叉指针，本身不承载可交付技术事实。执行 `non_fact_shell_closure`：若一个有明确 root 与 peer exit 的 subsection 从标题到出口只有“无”、空白、占位、裸外部指针，或不新增具体任务、流程、输出、时限和结果的泛化遵法/兜底 wrapper，则 root、空正文和 wrapper 整体排除；相邻前一技术表或履约章节的 membership 不能跨 peer 边界给这个空壳授予 membership。若四类排除载体移除后只剩这类非事实壳，正确范围为空；“保护标题和 source fidelity”不能把裸 `null` 变成只有标题/外部指针的非空结果。

企业内部制度、教程、产品说明书或其他非采购文件同样返回裸 `null`，即使局部内容与目标项目主题相关。

## 材料性错误

correctness repair 只有下列问题允许覆盖 candidate：

- 遗漏独立对象、专业系统、工作包、实施阶段、保障主题或详细载体；
- 只保留指针/概述而遗漏当前 Word 内详细原文；
- 将冲突项目、供应商成稿、非采购文档、四类排除载体、独立评分/资格/纯价格作为采购需求；
- 错误 `null` 或错误非空；
- 原生/Java-effective 输出不可消费。

普通同包噪声、重复、长度或风格差异不是材料性错误。

correctness 修改必须满足反事实技术写作测试：保持 Candidate 不变会导致下游技术方案的对象、工作包、独立章节、实施阶段、保障主题、具体事实基础、Owner 归属或上下文容量发生实质性错误。补入资格、商务、报价、纯评分、公告、须知、格式和合同模板内容不满足正向召回门槛。

删除还必须区分“非目标成员”与“材料性污染”。孤立标题、交叉指针、重复说明、少量评分/程序标签或其他普通同包噪声，即使在从零提取时可排除，只要不会把下游技术写作导向错误 Owner、项目、对象或工作内容，就不是 residual repair 的材料性错误。

四类硬排除载体和独立评分 Owner 不采用旧的高删除门槛：actual Owner 已确认且 exact removal 可与合格来源安全拆分时，即允许删除。大面积载体稀释、挤占或错误 Owner 属于 correctness；较小但完整、同质且可安全分离的载体可进入 `operational_precision`。其他普通同包噪声仍采用更高的不对称门槛，不能仅因“不理想”而删除。

删除范围必须精确且内部同质。提交或批准前必须检查范围内全部原子段落；四类排除载体内的技术性文字仍随载体删除，但若任一段属于合格采购需求、技术标准、项目专用技术条款、图纸说明或有效技术附件，则该宽范围不得整体删除，只能缩小到不伤害合格来源的子范围。不能可靠拆分时保留不可分割的混合段落；不要求输出逐段 ledger。

新增与删除分别承担举证责任。一个正确的新增不能为相邻内容自动提供删除理由；四类排除载体和独立评分 Owner 只有在自身 Owner、范围同质性与安全边界成立时才可移除，其他页数、否决、格式碎片或普通程序噪声仍不得搭载清理。混合 challenge 只有在 add 和 remove 各自通过对应门槛、共同修复同一边界时才成立。

correctness challenge 必须以反事实 final 关闭一个完整的 case-level 材料性问题。同一 Owner/membership 错误可以跨越多个不连续范围；这些范围不是多个无关 issue。Reviewer 必须在一次 challenge 中覆盖关闭该问题所需的全部安全可寻址岛，并在提交前重新检查 `Candidate + add - remove` 是否仍保留同类材料性错误。只修复一个局部岛而留下另一处完整硬排除载体，不构成 fixed。

反事实 final 为空时，必须额外证明 source 中所有位于四类硬排除载体之外的顶层区域和不连续 OUT 岛均无材料性正向目标。短小的技术标准、项目专用要求、图纸/设计说明或有效附件可夹在两个很长的排除载体之间；它们不因篇幅短、Candidate 未选或相邻内容庞大而失去 membership。若存在，应在同一个 case-level challenge 中 add 回合格范围并 remove 排除范围，而不是发布错误 `null`。

## 运营精度改善

`operational_precision` 不是第二套运行 profile，也不把 Candidate 重判为语义错误。只有 Reviewer 已完成整文身份、Candidate correctness、边界、外部召回和 source-fidelity 审查且未发现材料性语义问题后，才可考虑一次 remove-only challenge。

同一个 exact removal 必须同时满足：

- Candidate 已覆盖全部采购对象、工作包、实施阶段、保障主题和不可替代详细载体；
- 待删范围可独立寻址且 Owner 同质，不依赖关键词、标题或首尾推断内部内容；
- 对四类排除载体，待删范围逐原子段均属于同一排除 Owner 且不跨入合格来源；对其他普通噪声，逐原子段均不含唯一技术事实、采购对象、工作包、实施义务、必要上下文、参数/清单/图纸或其他详细载体；
- 删除不会让保留范围失去标题、表头、指代关系、上下文闭合或 source fidelity；
- 删除四类排除载体能使最终范围满足冻结 scope 合同；对其他普通噪声，删除还必须显著降低下游上下文、token、截断、注意力或证据池检索负担，而不是只减少少量噪声、重复句或让结果更整洁。普通噪声通常至少应覆盖一个完整自包含的非技术章节/附件，或约占 Candidate 文本的 10%；该比例只供模型结合内容判断，不由代码触发或裁决。

`operational_precision` 不能新增，不能与 correctness issue 混合，也不能用一个局部安全删除扩张到混合 Owner 的大范围。任一条件不能从完整 source 可靠证明时必须保留 Candidate。何为合格来源、排除载体、Owner、不可分割边界和材料性运营负担全部由模型判断；代码只能校验 issue type、范围方向和集合关系。

## 地址合同

只有 canonical source 行首的 `段落N：` 中 N 是地址。正文内章节号、条目号、数量、日期、型号和引用数字都只是内容。

最终只能是空 ranges（代表裸 `null`），或 `段落N` / `段落N-段落M` 的合法集合。

若提供可选 Word 结构图，它只包含从同一 DOCX 机械抽取并与 source block 高置信对齐的 body 顺序、段落/表格类型、样式、outline、编号、字号、粗体、对齐、分页、表格规模和 outline ancestry。`sc=node@parent~exit` 表示该节点当前所属的机械 outline scope、最近上级和第一个同级或更高层级结构出口；它适用于标题、普通段落和表格。模型可用它判断某个内容与后续内容是否处于同一物理层级、何处出现待核实的 peer boundary，但不得把结构出口或任一格式属性直接等同于公告、合同、响应格式或采购需求 Owner。若 exit 节点经 source 判断仍属同一 Owner，必须继续沿下一 scope 传递；结构图未列出的普通 block 仍须从完整 source 文本判断，缺少结构节点不是排除证据。

结构图存在时，任何拟保留岛都必须完成一次 ancestry closure：读取其 `sc` active node、最近上级 outline 节点及对应 source 文本，确认两者 Owner，并指出是否已经到达 `exit`。若 active scope 或上级是四类硬排除载体且出口尚未出现，该岛继续继承排除 Owner；技术性强、标题像任务书/规范/清单、详细参数表或被其他章节引用都不能替代真实结构出口。此检查只形成一次 Owner/边界结论，不要求逐 block ledger。

Reviewer 的删除表达是一个互斥对象。语义 final 完全收敛后，同时计算 Candidate 内完整删除岛和完整保留岛：删除岛数量不多于保留岛时使用 `removal.mode=exact`，该分支只存在 `remove_ranges`；保留岛更少时使用 `removal.mode=candidate_complement`，该分支只存在 `preserve_ranges`，Harness 计算 Reviewer 提案 `proposed remove = Candidate - preserve`；平局使用 `exact`。整文 veto、`source_role=non_procurement` 或 `instantiation=absent` 的非空 Candidate 必须形成零保留岛，并以 `candidate_complement + preserve_ranges=[]` 表达。地址压缩只能发生在语义判断之后，不能用 Candidate 宽度、删除比例或书写便利决定 membership。每个保护 range 应完整位于一个 `candidateRanges` interval 内，遇到 OUT block 必须拆开；若模型误跨 OUT gap，Harness 只能机械取其与 Candidate 的交集，保护模式绝不会把 Candidate 外 block 加入 final。非空 preserve 若与 Candidate 完全无交集必须 fail-closed。若旧字段或非法结构同时表达 remove 与 preserve，Harness 必须 contract-fail 并保留 Candidate，不能用集合冲突消解替模型选择语义方向。

Reviewer 的结构字段必须是已收敛语义结论的无冲突投影。若 reason 明确认定任一 Candidate block 或保留岛属于 requirement，`exact` 删除必须在该岛前后拆分；若使用 `candidate_complement`，则必须把该岛完整写入 `preserve_ranges`。Harness 只机械计算 effective removal，不解释 reason，也不生成第二份保护集合。

进入独立 Release 后，`removal.mode` 只记录 Reviewer 如何表达删除提案。机械归一化后的 effective removal 本身就是完整 remove envelope，并标记为 `REMOVE_REVIEW`；challenged add 标记为 `ADD_REVIEW`；其余 Candidate 标记为受保护 `BASE_KEEP`。Reviewer 的 reason、证据线索和原始 `preserve_ranges` 不进入 Release。Release 必须攻击 `REMOVE_REVIEW` 是否造成材料性遗漏或上下文断裂，独立判断 `ADD_REVIEW` 是否有合法 Owner 与事实负载，并对完整 Candidate 执行一次四类硬排除载体 sweep。`REMOVE_REVIEW ↔ BASE_KEEP` 的切换只是权限 marker，不是语义 exit；若 source-proven 四类 root 跨过该切换，Release 必须继续穿过后续 OUT 或其他 marker，直到首个不同 Owner 的 peer root 或 EOF。只有同一省略 block 被模型写入 `hard_excluded_ranges` 时，Release 才可越过 `BASE_KEEP`；载体外普通 false protection 仍不得越界，未挑战 OUT 仍不得加入。标记不构成语义投票，代码不得依据 reason 补充或删减语义范围。

Release 的唯一终态工具按 `hard_excluded_ranges -> outside_carrier_excluded_ranges -> reason -> final_ranges` 生成。`hard_excluded_ranges` 可承载任意 Candidate 或 `ADD_REVIEW` 中已证明属于四类硬排除载体、且准备省略的 block；它是 Candidate 全域四类载体 veto 的 typed authorization。`outside_carrier_excluded_ranges` 仍只承载授权 envelope 内、已经证明位于四类载体之外、经过主要直接效力与 `duty_survival_attack` 后可安全分离的非 requirement atoms。两个字段都不是逐 block ledger。`final_ranges` 是唯一权威完整集合。Harness 先将 final 裁剪到 Candidate 与 challenged add；省略的 `BASE_KEEP` 只有同时出现在 `hard_excluded_ranges` 才保留省略，其余机械恢复。随后 Harness 从两个 exclusion 字段移除 final 已保留地址、按各自权限裁剪并消除重叠；它不得用字段覆盖 final，不识别载体或 atom 语义，也不生成或扩张 exclusion ranges。

remove envelope 的大小、字符覆盖率或偶然覆盖完整 Candidate 只描述机械权限边界，不表达应删除多少内容。Release 必须逐原子判断 challenged 子集；100% envelope 既不要求全删，也不允许因其中存在一个合格岛而整包恢复。

Release 的 `final_ranges` 若越过机械权限，Harness 只做集合约束：只允许包含 Candidate 或 Reviewer challenged add；所有不在 remove envelope 内、且未被同一提交的 `hard_excluded_ranges` 明确授权为四类载体 omission 的 Candidate block 都机械恢复。Release 只能恢复或省略 `REMOVE_REVIEW`、接受或拒绝 `ADD_REVIEW`，并通过该唯一 hard-carrier veto 省略受保护 Candidate。该裁剪不改变任何段落的语义判断。
